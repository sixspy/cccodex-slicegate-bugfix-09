# 筛选一致说明

- **生效日期**：2026-11-17（口径当日禁止改口；改口须次日新口径另立说明）
- **选定处置**：**乙处置** —— 列表只作提示，放行写前现场重算完整度，未完整则零写入并追加筛选偏离流水
- **被否方案**：甲处置（服务端物化可放行键快照）——本系统单机 SQLite 即可承载现场重裁，不引快照层

## 一、同源裁决

可放行集合与放行写入必须同源裁决，唯一裁决函数为 `backend/app.py: adjudicate()`：

- 完整 ⟺ `expected_count > 0` 且 `row_count >= expected_count`
- `row_count > 0`（未达完整）为 部分完整；否则 待检
- **可放行 ⟺ 现场重裁为完整 且 `release_status = 未放行`**

筛选列表（`GET /api/slices`）、切片详情（`GET /api/slices/{id}`）、放行闸（`POST /api/slices/{id}/release`）
三处共用同一函数现场重裁；`slices.completeness` 存储列仅为登记/重裁时的缓存，**一律不作放行依据**。
禁止靠前端正放宽筛选绕过完整度；禁止把应拒绝项画成可点成功（前端对不可放行项禁用放行按钮，
且按钮状态只取服务端下发的 `releasable` 标记，前端不自立口径）。

## 二、放行闸写入一径

放行写入只有一条路径，在 `BEGIN IMMEDIATE` 写事务内依次裁决：

1. **筛选口径校验**：请求携带的筛选条件（业务日/分区/完整度）必须命中切片本身且不与现场重裁冲突，
   否则记 `deviations.kind = 筛选口径偏了` 并拒绝（409），零写入。
2. **现场重算完整度**：未完整则记 `deviations.kind = 筛选偏离`（含实收/期望与操作人），
   拒绝（409），**零写入**——不写 releases、不写 watermarks、不改 release_status。
3. **争用裁决**：切片已放行，说明同一筛选条件下有值班先到，本次为后手，
   记 `releases.status = 争用`（note 标注筛选争用，附筛选口径 filter_key 与操作人），拒绝（409），零写入。
4. **放行**：完整且未放行，同事务写 `release_status = 已放行` + `releases.成功` + `watermarks` 水位。

同一筛选条件下两名值班同时抢点放行：写事务经 `BEGIN IMMEDIATE` + 忙等超时排队，
先到者放行，后手在事务内重读到已放行，按第 3 条标注筛选争用。绝不双写成功、双写水位。

## 三、对齐可查

筛选列表、放行闸、切片详情、处置页（放行流水 + 筛选偏离流水）、策略条（`GET /api/policy`）
五处口径一致、均可查询核对；任何一次闸口拒绝都在筛选偏离流水中留痕（类型、说明、筛选口径、操作人、时间）。
